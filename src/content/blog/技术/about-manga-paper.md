## 为什么做 MangaPaper

我一直觉得，技术博客不一定非要长得像技术博客。

常见的博客主题大多追求简洁、规整和信息密度。阅读体验固然重要，但看久了，也容易发现许多博客逐渐变得相似。我更喜欢纸张、手写稿和漫画分镜带来的质感：清晰的边界、随性的细节，以及恰到好处的留白。

于是有了 MangaPaper。

它是一个漫画稿纸风格的开源博客模板。点阵纸背景、粗墨色边框、单向硬阴影、略微倾斜的彩色标签，再配上一套全站等宽字体，构成了它最直观的视觉特征。

我希望它既保留纸质媒介的温度，也有技术博客应有的清晰和秩序。文章可以很长，代码可以很多，页面依然应该容易阅读；视觉可以有个性，但不应该成为内容的负担。

**MangaPaper 不只是给博客换一套皮肤，而是尝试建立一套贯穿页面布局、字体、文章卡片与分享图片的设计语言。**

- **在线预览：** https://lavieio.com/
- **GitHub 仓库：** https://github.com/lavieio/manga-paper-template
- **项目许可：** MIT

## 一张稿纸应该是什么样的

### 点阵、墨线与贴纸

MangaPaper 的视觉语言来自几个简单的元素。

- **点阵纸底**：细小、规则的墨点铺满背景，营造纸张质感，同时尽量避免干扰正文。
- **硬边框与硬阴影**：卡片使用清晰的墨色边框和单方向偏移阴影，不依赖模糊的浮层效果，呈现纸片叠放般的视觉层次。
- **贴纸式标签**：分类标签使用不同颜色和轻微旋转，就像贴在纸面上的便签，为页面增添一点活泼感。
- **等宽字体**：标题、正文、代码和界面文字尽量采用统一的字体系统，让整站更接近一份经过排版的技术手稿。
- **明暗双主题**：沿用同一套布局和组件，通过切换颜色变量适应不同光线环境，让明暗主题保持一致的视觉语言。

这些元素并不复杂，关键在于控制它们的比例：边框要有存在感，但不能太重；标签可以活泼，却不能抢过标题；背景需要质感，也不能让人忘记自己正在阅读文字。

我想要的不是一张堆满装饰的漫画海报，而是一张真正可以用来写字、阅读和记录的稿纸。

### 首页不是传统的信息流

首页采用纸片式精选文章轮播，并结合最近更新、分类、标签和归档组织内容。

精选文章像叠放在桌面上的几张纸片，帮助读者快速发现重要内容；文章列表则尽量保持清晰，不用大量装饰图片填满页面，让注意力回到标题和摘要上。

GitHub、RSS、邮箱等快捷入口也融入首页的贴纸式设计。入口的顺序和图标由配置控制，RSS 等站点功能则由模板统一提供。

我希望首页同时具备两种属性：第一次访问时，它能展示博客的个性；经常回来时，它又能让读者迅速找到最近更新的文章。

## 为长篇技术文章打磨阅读体验

技术博客与普通内容站点有些不同。文章里可能有很长的目录、代码块、表格、截图和外部图片。如果只关注首页设计，真正进入正文后，阅读体验仍然可能不够理想。

因此，MangaPaper 的不少功能都围绕文章本身展开。

### 目录与代码块

长文章支持右侧固定目录，滚动时自动高亮当前位置，并通过朱砂色指示条标识阅读进度。屏幕较窄时，目录会收进弹层，避免占用正文空间。

代码块提供一键复制按钮。无论是配置文件、Shell 命令还是较长的代码示例，都可以直接复制使用，不必手动选择整段文本。

这些功能看似普通，却能显著减少阅读技术文章时的额外操作。

### 图片与布局稳定性

文章中的图片支持 PhotoSwipe 灯箱。点击图片后即可进入大图查看，相关交互逻辑按需加载，避免一开始就让完整的灯箱功能参与页面加载。

图片尺寸也尽可能在构建阶段确定。对于能够读取到尺寸的本地图片和外链图片，模板会补充宽高信息，降低图片加载后挤动正文的风险。

这些细节未必能在首页截图中体现，却会直接影响长篇文章的阅读体验。对我来说，好的设计不仅要看起来舒服，也要在实际使用中保持稳定。

### 搜索、归档与分类

博客提供文章归档时间轴、标签云、分类页和静态全文搜索。

搜索由 Pagefind 提供，索引在构建阶段生成，并支持中文检索。整个过程不需要额外部署搜索服务器，比较适合以静态托管为主的个人博客。

文章列表采用分页方式组织，每页默认显示 8 篇。草稿、公开文章和私密文章则遵循不同的处理规则，不会简单地把所有 Markdown 文件都展示出来。

从首页发现文章，到通过分类和标签浏览，再到使用全文搜索定位内容，这些功能共同构成了博客的内容组织方式。

## 字体：不让中文成为性能的负担

等宽字体是 MangaPaper 视觉设计的重要组成部分，也是这个项目中花费了不少精力打磨的地方。

我选择了 [Maple Mono NF CN](https://github.com/subframe7536/maple-font)。它兼顾中英文字符和代码阅读，也能让标题、正文与界面保持统一的字体风格。字体采用 SIL Open Font License 1.1 许可证。

但中文字体有一个现实问题：字符数量庞大，完整字库的体积也不小。如果直接加载整套字体，浏览器就可能为当前页面根本没有用到的字符付出额外成本。

因此，MangaPaper 将字体优化融入构建流程，而不是要求使用者手动维护字体文件。

### 从完整字库到按需加载

字体源文件保存在仓库的 `assets/fonts/` 中，构建时根据站点实际内容生成自托管的 WOFF2 字体子集。

在近期的字体优化中，我又进一步调整了这条管线：

- **按页面拆分子集**：根据页面实际使用的字符生成字体资源，减少加载当前页面不需要的字形。
- **区分核心字符与扩展字符**：优先满足站点界面、常用符号和首屏文字的显示需求，其他字符则由相应的字体子集补充。
- **对齐 fallback 字体度量**：当主字体没有覆盖某些字符时，使用经过度量调整的回退字体，尽量减少字体切换引起的宽度变化和布局偏移。
- **统一构建管线**：开发与构建流程复用同一套字体生成机制，修改文章后无需手动重新制作字库。

这些优化的目标并不是简单地减少字体文件数量，而是让浏览器尽可能只为当前页面真正需要的内容下载字体，同时保持排版的稳定性。

字体优化也不是一次性工作。不同页面的字符覆盖范围、字体请求数量、CSS 大小和实际渲染效果都需要放在一起考虑，不能只看某个文件缩小了多少。

对中文博客来说，字体既是视觉设计的一部分，也是页面性能的一部分。我希望这两者不必互相牺牲。

## 纯静态，不代表功能需要做减法

MangaPaper 基于 Astro 构建，输出纯静态站点，不需要为博客本身运行 SSR 应用服务器。

文章、分类、归档、RSS、站点地图和分享卡片都可以在构建阶段生成。浏览器端只在需要交互的地方加载相应脚本，例如主题切换、文章目录、图片灯箱和私密文章解锁。

这种架构带来了几个直接的好处：

- **部署简单**：可以使用 Vercel 或 Cloudflare Pages 等静态托管平台。
- **维护成本低**：博客正文不需要依赖数据库或持续运行的应用服务器。
- **内容分发方便**：静态页面和资源可以直接通过 CDN 分发。
- **构建过程可检查**：许多内容规则和生成结果都可以在发布前验证。

当然，纯静态架构也有边界。评论和访问统计等能力依赖外部服务，不会凭空从静态文件中产生。因此，MangaPaper 将它们设计成可选集成，而不是要求每个使用者都采用同一套服务。

### 自动生成分享卡片

每篇公开文章都可以在构建阶段生成独立的 1200 × 630 OG 分享图。

卡片使用 Satori 和 resvg-js 渲染，将文章标题、作者等信息按照统一模板排版。这样，在社交平台分享不同文章时，就能展示与正文对应的预览，而不必为每篇文章手工制作图片。

分享卡片本身也是整套设计语言的一部分。它不是简单截取一张网页，而是将稿纸质感、字体风格和标题排版延伸到站点之外，让文章在被分享时依然保有 MangaPaper 的辨识度。

草稿和私密文章不会生成公开分享卡片，避免不应公开的内容通过预览图泄露。

### 按需启用外部服务

MangaPaper 支持按需启用一些常见的博客服务：

- **remark42**：为公开文章提供评论。
- **Google Analytics 4**：统计站点访问情况。
- **Google Search Console**：支持 HTML 标记验证，也可以在域名服务商处配置 DNS TXT 验证。
- **Vercel Web Analytics / Speed Insights**：在 Vercel 上按需启用访问分析和性能监测。

这些集成通过环境变量配置。未启用的集成不会主动加载对应脚本，相关的部署响应头也会根据配置生成。

对于不需要评论或统计服务的博客，保持默认配置即可，不必为了一个可选功能手动修改整套部署文件。需要时再启用，也能让站点的默认依赖保持简单。

## 私密文章：把加密纳入静态构建

这是 MangaPaper 相较于普通静态博客，一个更有针对性的功能。

有些内容并不适合公开展示，但又不一定需要一整套用户系统。例如个人笔记、阶段性记录，或者只希望与少数知道密码的人分享的文章。

针对这样的场景，MangaPaper 提供了构建期加密和 `/private` 入口页。

在文章 frontmatter 中设置：

```yaml
---
title: 一篇私密文章
private: true
---
```

构建阶段会使用配置的密码加密文章内容，发布到静态站点的是密文。访客进入 `/private` 页面后输入密码，浏览器通过 PBKDF2（SHA-256，600,000 次迭代）派生密钥，再使用 AES-256-GCM 解密内容。

解锁状态默认保存在当前浏览器中一小时，也可以通过环境变量调整。

除了正文加密，私密文章还会从公开文章列表、归档、标签、分类、RSS、sitemap 和搜索索引中排除，避免在普通浏览路径中暴露。

不过，这个功能有明确的安全边界：**加密静态页面不等于完整的账户权限系统，也不能替代对源文件的保护。**

原始 Markdown 在构建前仍然是明文。如果文章内容确实需要保密，承载这些文章的 Git 仓库必须设为 Private；同时应更改模板默认密码，并妥善保管自己的密码。密码丢失后，已有密文无法直接恢复。

我更愿意将它定位为适合个人博客场景的密码保护内容功能，而不是将其包装成适用于所有敏感数据的安全系统。它解决的是个人写作中一类具体的需求，而不是替代成熟的身份认证和访问控制机制。

## 写作流程也应该省心

为了减少维护博客的重复劳动，MangaPaper 对文章元数据做了一些自动化处理。

文章使用 Markdown 编写，放在 `src/content/blog/` 目录下。一级子目录名就是分类，文件名就是 URL slug。标题、摘要、标签、是否精选、草稿状态和私密状态则通过 frontmatter 管理。

文章的 `date` 和 `updated` 也可以交给 Git Hooks 自动维护：

- `feat(blog): 发布新文章`：为新文章写入日期，或更新已有文章的修改时间。
- `fix(blog): 修正文章错字`：修复问题时不刷新 `updated`，`chore` 类提交也遵循这一规则。
- 提交信息包含 `[skip-updated]`：显式跳过修改时间刷新。

这样可以尽量避免每次编辑文章时都手动修改日期字段，也能让文章的发布时间和更新时间更符合实际维护过程。

站点本身的名称、作者、简介、分页数量和快捷入口则集中在根目录的 `manga-paper.config.ts` 中。关于页正文单独存放在 `src/content/pages/about.md`，可以使用 Markdown，也可以按需要编写 HTML 和局部样式。

我希望使用者修改站点时，能够把精力放在文章和内容上，而不是到处寻找配置项。

## 写在最后

MangaPaper 是一个仍在持续打磨的项目。

对我来说，它最有意思的地方并不是把多少功能塞进一个模板，而是尝试让设计、写作和工程实现彼此配合：稿纸风格贯穿整个站点，字体优化融入构建流程，私密文章有明确的实现边界，可选服务也遵循按需启用的原则。

我希望它既可以是一个有辨识度的个人博客，也可以成为一个容易部署、方便修改、适合长期写作的起点。

如果你也喜欢这套设计，欢迎查看源码、创建自己的仓库，或者通过 GitHub Issues 提交建议。
